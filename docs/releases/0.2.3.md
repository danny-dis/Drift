# Drift 0.2.3

This release makes saved work easier to find and edit. Mind map and Wiki now have their own pages, and thoughts, ideas and projects have add, edit, archive and restore controls.

## Find and manage your work

The workspace has ten direct destinations: Thoughts, Ideas, Projects, Mind map, Wiki, Office, Research, Activity & budget, Needs approval and Workspace. You can bookmark them, reload an entity detail page and use browser Back and Forward. On smaller screens, the page selector replaces the tab row.

Thoughts, ideas and projects have list and detail screens with add, edit, archive and restore controls. Search covers saved history rather than just the newest batch. Failed input stays in the form, and revision conflicts ask you to reload instead of silently overwriting someone else's edit.

Editing a thought changes its current text, not the immutable original capture. Existing AI suggestions remain separate from both. Archive hides work from the active views and holds unfinished processing. Restore makes the record visible; it does not approve paused tasks or recreate missing multipart work.

## Open the mind map and wiki directly

Mind map uses the stored relationships between thoughts, ideas and projects. Its nodes open the corresponding details, and the equivalent list supports keyboard use. It does not invent links from display order.

Wiki creates source-linked pages only after you confirm a generation request. Choose a project by name or use all active saved work. Pages show their queue or completion state, source changes, omitted or shortened context, retained errors and unfinished output. Reading or refreshing a page does not request another generation. See the [Wiki guide](../wiki.md).

Mercury 3 acceptance tests generated a real wiki page and processed a thought into an advisory answer. Both results survived restart. Reading the page and retrying the saved capture used no further model calls. These tests used disposable data, not the owner's notes. AI still needs a reachable provider and available call allowance, and its output remains unverified.

## Storage, processing and performance

- Archive checks cover intake, task selection, approvals, tool execution and response publication. An answer already in flight cannot be unsent, but archived work must not publish its result as a new thought or report.
- Task approval records the source revisions it covers. An older approval does not authorize work across a later archive and restore.
- Project tasks and background planning/reflection also check the sources they actually use. Archiving one idea does not stop unrelated active work in the same project.
- Generated planning files remain readable, but their text is not treated as owner instructions. Reflection checks its sources again when its storage worker starts.
- Wiki source selection and execution follow capture, idea and project lineage, so an archived idea cannot return through its still-readable original or another linked projection.
- Editing a held, restored source requires reapproval too. A new confirmed wiki request has its own permission and does not resume older tasks.
- Watcher and attention checkpoints refresh before making targeted updates, so a stale writer cannot restore an archive or overwrite a newer path edit.
- SQLite schema inspection and migration share a write transaction. A partial migration rolls back.
- Queue selection and archive sweeps share one metadata snapshot per operation instead of rereading the ledger for every task. Execution boundaries still check fresh state.
- Idea lists and mind-map rendering share a request-local snapshot too. In the 40-projection regression, metadata reads fell from 79/80/40 for the three checked views to one each; this is a read-count result, not a claim of a matching speedup.
- An interrupted wiki handoff keeps its source snapshot. Reopening links a uniquely saved task or reports a blocked request with a recovery instruction; it does not silently queue another model call.
- Applying another blocker preserves a wiki task's resumable phase, so a fresh approval after reviewing restored sources can still work.

## Checks and limits

Real HTTP and browser checks covered creating, editing, archiving and restoring disposable work. Browser acceptance covered all ten pages at 320, 390, 768, 1024 and 1440 pixels, including source links, Back navigation, budget blocking and error recovery. All 19 frontend checks, TypeScript and the production build passed.

Local Windows runs on Python 3.12 and 3.13 each passed 874 tests, with one host-dependent symlink case skipped. A clean wheel installation served the bundled dashboard, and its 53 Python modules matched the tested source. The full frontend dependency audit reported no known vulnerabilities. Independent reviews checked the repaired privacy and recovery paths.

The [release workflow](../../.github/workflows/release.yml) also requires the Windows/Linux Python 3.12/3.13 matrix before publishing its packages. These checks do not prove that generated answers are true or that Drift can run unattended for weeks. Review the sources and keep backups.

## Upgrade

Stop the running Drift process and back up its box. Then install the new wheel:

```bash
python -m pip install --upgrade "https://github.com/danny-dis/Drift/releases/download/v0.2.3/drift-0.2.3-py3-none-any.whl"
python -m drift.main --box ./drift_box --name Drift
```

Use your existing `--box` path, not a new empty folder. Installing a package does not upgrade an already running process; restart it after installation. Your provider settings and any blocked tasks still need your review. Disk usage at 90% or more continues to report degraded health.
